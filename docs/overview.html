Business scenario

A utility sells electricity and gas to residential customers. Two operational systems feed the warehouse: Billing (contracts, meter readings, invoices, payments, tariffs, tax lines) and CRM (customers, addresses, campaigns, call-centre contacts).

1. Source change

Billing v1 and CRM v1 are replaced by v2 with new keys and renamed columns. The cut-over date is 2026-01-04 (dbt var cutover_date). History must not break and consumers must see no change.

2. Platform move

The warehouse moves from Snowflake to Databricks. dbt and Airflow stay. The same models must give the same numbers on both platforms.

Consumers are four data products: billing (revenue by tariff and month, open receivables), sales (new contracts, churn), tax (VAT and energy-tax lines per invoice) and call centre (contacts per customer, first-contact resolution).

Architecture

Each layer has one job. Data moves down one layer at a time, and every layer is tested.

Existing diagrams, rendered by GitHub: platform, vault model, source change and migration, Mermaid source.

Source-system change without breaking consumers

  • Raw and staging: v2 gets new tables and new staging models. v1 keeps its history and gets no new rows.
  • Hubs and links: v1 and v2 keys live in the same hub. Key formats never collide, so no key is rewritten.
  • Same-as links: one row per key_map row links the v1 key and the v2 key of one business entity.
  • Satellites: v2 attributes get new *_v2 satellites. v1 satellites are closed, not dropped.
  • Business vault: bv_*_master gives one master key per entity. A v2 key with a same-as row takes the v1 key. Every other key is its own master.
  • Marts: they read both versions through master keys and map v2 columns to the same mart columns. A re-issued v2 invoice replaces its v1 invoice and is not counted twice.

Proof: mart_vs_expected_totals.sql shows mart totals equal expected totals after each load date, 2026-01-01 to 2026-01-05. Tests assert_v1_satellites_closed_after_cutover and assert_unmapped_keys_survive guard the rules. Details: docs/source-change.md.

Migration: Snowflake to Databricks

One dbt project builds on both targets. Models contain no if target.type. Dialect gaps live in macros that use adapter.dispatch.

MacroGap it closes
month_truncdate_trunc returns DATE on Snowflake and TIMESTAMP on Databricks. The macro keeps invoice_month a DATE on both.
hex_keyHash keys are BINARY on Snowflake and hex STRING on Databricks. The macro compares both as upper-case hex.
copy_into_rawDifferent copy into syntax: stage and column position on Snowflake, volume and header names on Databricks.

Reconciliation and cut-over

  • recon__table_stats returns one row per table: row count, distinct keys, key min and max, key checksum, hashdiff checksum, measure sums.
  • scripts/compare_recon.py compares the two JSON outputs and exits 1 on any differing cell. Evidence is committed in data/recon/.
  • Plan: parallel run, daily recon, go when recon is clean for N consecutive load dates, switch consumers group by group, then switch the Airflow loader.
  • Rollback: Snowflake loads keep running through a 14-day window, so consumers switch back with no replay.

Details: migration.md, cutover.md, performance.md.

CI/CD and orchestration

Pull request

  • sqlfluff lint, dbt parse, pytest.
  • Slim CI: state:modified+ with --defer against the prod manifest.json published on GitHub Pages.
  • The job waits while a prod deploy runs, so the manifest is current.
  • Builds into a schema per PR and drops it at the end.
  • Job attribution fails the build on AI co-author trailers.

Main

  • Deploy builds the prod target one load date at a time (scripts/build_by_load_date.sh).
  • Runs in environment prod with secrets from GitHub, none in YAML.
  • dbt docs generate, then publish to GitHub Pages together with this page and the manifest.

Airflow

DAG vdwh_transform runs once per logical date (@daily, max_active_runs=1, 2 retries). Steps: dbt_deps, dbt_seed, load_raw, then one Cosmos task group per layer (staging, raw vault, business vault, marts), then cross-layer tests. The load date comes from the Airflow ds. The target comes from env var DBT_TARGET, so the DAG logic does not change per platform.

Lessons learned

  • Re-running a past load date must be a no-op. automate_dv compares only with the newest row per key, so a replay inserted rows again. Now no table inserts a key with the same or a later load datetime (loading.md).
  • Slim CI must wait for the prod deploy. It defers to the manifest on Pages. During a deploy that manifest is stale, so the job waits.
  • Payments need dedup per source. The v2 feed repeats v1 payments of migrated invoices. fct_payment numbers rows inside each source and pairs v1 with v2, so two equal instalments stay two payments.
  • Identifier case differs. Snowflake folds to upper case, Databricks to lower case. Staging columns stay upper case, and information_schema queries compare with upper().
  • Hash types differ, hashing does not. The fix is to compare keys as hex, not to change the hash.
